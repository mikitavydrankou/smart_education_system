## Data and RPC contract

Use a user-scoped Supabase client with `.schema('lms')`. `courses` is publicly readable when published; `course_catalog` additionally supplies `teacher_name` for published courses. Other readable tables are filtered by RLS; all mutations use RPC. `revisions` is private, including its answer keys. Anonymous users cannot query lesson content. Students must complete the verified assessment before requesting enrollment.

- `save_course({payload: {id?, title, description, published}})` → UUID.
- `request_enrollment({course})` and `review_enrollment({course, student, approve})` → void. Rejected requests can be requested again; pending/approved requests remain unchanged.
- `save_lesson({payload: {id?, course_id, title, position, published, threshold, content, questions}})` → UUID. Every save creates an immutable revision. `published:false` saves a draft without replacing or hiding an existing published lesson; public title/order remain unchanged. `published:true` replaces the public revision and clears the draft pointer. Existing student progress stays pinned to its first accessed revision.
- Content is an array of `{id, styles: ['visual'|'auditory'|'kinesthetic'], blocks: [...]}`. Assign a style at most once. Render block text safely; never interpret HTML.
- Questions contain `{id,type,prompt,options,answer}`. Types: `single` (integer option index), `multiple` (integer index array), `boolean` (boolean), `short` (array of accepted strings), `matching` (object mapping left IDs to right IDs), `ordering` (ordered array of item IDs). Student answers use the same representation, except `short` is one string.
- Every question except short answer requires at least two unique, nonblank string options; boolean requires exactly two labels. Matching options encode `left|right` pairs and must agree exactly with their answer mapping.
- `get_lesson({lesson,preview?:false})` → lesson fields plus `revision_id`, `content`, `questions`, `threshold`, `passed`. Student responses strip `answer`; the owning teacher receives keys for editing except in preview.
- `create_study_session({lesson,variant,preview})` → `{id,completed_blocks,completed}`. A new session starts material from the beginning, including after a format switch. `record_study_block({study,block,answer})` accepts only the next block; interactive practice must be answered correctly.
- `start_attempt({lesson,preview,study})` → attempt UUID, requiring a completed matching study session. Owners must use preview; students must not. `submit_attempt({attempt,answers: {[questionId]: answer}})` → `{id,score,total,percentage,passed,preview}`. Submission locks its row and repeated calls return the original result. Passing updates progress in the same transaction.
- Migration 005 adds study sessions and publication validation for interactive practice. Practice activities use `{type:'single',options:string[],answer:number}` or `{type:'ordering',options:string[],answer:string[]}`. Incomplete drafts remain permitted.
- Migration 006 adds teacher-only, idempotent `create_demo_course({})` → course UUID. The teacher dashboard button creates a published three-lesson Internet course with three formats and all six quiz types; it does not enroll or approve students automatically.
- `save_assessment({answers,selected_style:null})` → `{completed:false,source_pending:true}` until approved config exists. Draft answers map question IDs to zero-based option indexes. Complete answers return `{completed:true,style,scores}` or `{completed:false,tied_styles,scores}`; resubmit with a tied `selected_style` to resolve ties. `set_preferred_style({style})` updates the independently selected format.

The public lesson list exposes metadata to approved students; content access and attempt creation additionally enforce a completed assessment and all earlier published lessons passed. Draft lessons are visible only to their teacher. Teacher preview enforces earlier published lessons passed in preview attempts, independently from student progress. Profiles expose only the current user and students enrolled with the current teacher. Student matching questions contain only left-hand `options` and independently sorted `rightOptions`; ordering choices are sorted independently of their answer key.

## Private files

Upload to `lms-files/<courseUUID>/<lessonUUID>/<unique-filename>`. The bucket accepts JPEG/PNG/WebP images, supported audio, and PDF. Total maximum is 20 MB; image maximum is 5 MB. Owners upload and read their course files. Students can list or sign only files explicitly referenced by image/audio/PDF blocks in their pinned revision (or the current published revision before first access), while lesson access remains authorized. Draft-only and newer unpinned revision media stay inaccessible. The generated `/api/lms/files?path=` URLs encode slash separators as `%2F`; filenames use safe ASCII letters, digits, dots, underscores and hyphens. Validate size/MIME in the upload handler as well. Generate short-lived signed URLs with the user-scoped client, never public URLs. Storage supports no student upload, overwrite or deletion policy.

## Release verification

For a local browser run, use `pnpm test:e2e:lms`; the script privately reads the local instance settings, builds with those public values, and runs the LMS/catalog browser suites. Use `pnpm test:e2e:lms --all` for all browser checks. The script never installs fixtures on a hosted project. Rebuild normally with deployment environment values before publishing.

Run `pnpm exec supabase test db` after `pnpm exec supabase start`. The transactional pgTAP fixtures cover anon, student, pending student, approved student and unrelated teacher. Check direct reads of revisions fail; profile role writes fail; locked lesson RPCs fail; failed tests preserve locks; repeated submissions preserve original scores; preview creates no progress; later revisions preserve pinned progress. Validate email sessions and storage URLs on Netlify. No hosted migration, SMTP configuration or deployment is implied by committing this migration.
